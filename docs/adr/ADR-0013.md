# ADR-013: WAL の形式とコミット・リカバリの手順を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Transaction の次に WAL / Recovery を実装する。完成条件は次のとおりで、意図的にプロセスを停止させるクラッシュテストを追加する。

- commit 済みの変更をクラッシュ後に復元できる
- 未 commit の変更を復元時に適切に処理できる

ADR-0012 では no-steal 方式を採り、コミット前の変更はディスクに書かないとした。一方でコミットの flush は複数のページを順に書くため、その途中でクラッシュすると変更の一部だけがディスクに残る。これまでの ADR でも、ページの確保と初期化の間（ADR-0004）、行とインデックスの書き込みの間（ADR-0009）、UPDATE での行の移動（ADR-0006）のクラッシュを、本ステップの課題として残してきた。

## Decision

### 方式

- **REDO のみの物理ログ** とする。ログにはページの変更後の内容（ページイメージ全体）を書く
- no-steal（ADR-0012）なので、コミット前の変更が DB ファイルに書かれることはなく、UNDO は不要である
- コミットのたびにチェックポイント（DB ファイルへの反映とログの切り詰め）まで行う

### WAL ファイル

- WAL は DB ファイルと同じディレクトリの `{DB ファイル名}-wal` とする
- WAL がなければ DB を開くときに作る。空の WAL は「反映待ちのコミットがない」ことを表す

WAL は、ヘッダの後にレコードを並べたものとする（リトルエンディアン）。

ヘッダ（16 バイト）:

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 8 | マジックバイト列 `b"SQLTOYWL"` |
| 8 | 4 | WAL のフォーマットバージョン（`u32`、`1`） |
| 12 | 4 | ページサイズ（`u32`、`4096`） |

ページレコード:

| サイズ | 内容 |
| --- | --- |
| 1 | レコード種別（`1`） |
| 4 | Page ID（`u32`） |
| 4096 | ページの内容 |
| 4 | CRC-32（種別からページの内容までに対して） |

コミットレコード:

| サイズ | 内容 |
| --- | --- |
| 1 | レコード種別（`2`） |
| 4 | コミット後の DB のページ数（`u32`） |
| 4 | このコミットのページレコードの数（`u32`） |
| 4 | CRC-32（種別からページレコードの数までに対して） |

- CRC-32 は IEEE 802.3 の多項式（`0xEDB88320`、反転入出力）とし、依存ライブラリを使わずに実装する
- 1 回のコミットは「ページレコードの並び + コミットレコード」で表す

### コミットの手順

バッファプールの flush（ADR-0011）を次の手順に置き換える。dirty なページがなければ何もしない。

1. dirty なページを Page ID の昇順にページレコードとして WAL の末尾に書き、続けてコミットレコードを書く
2. WAL を fsync する。**この時点をコミットの完了とする**
3. 同じページを DB ファイルに書き、DB ファイルを fsync する（チェックポイント）
4. WAL をヘッダだけに切り詰めて fsync する

### リカバリの手順

DB を開くとき、Page Manager がヘッダページを検証した後、バッファプールを使い始める前に次を行う。

1. WAL のヘッダを検証する。マジック・バージョン・ページサイズが合わなければエラーとする。ヘッダが途中までしかない（WAL の作成中にクラッシュした）場合は、空の WAL として作り直す
2. レコードを先頭から読む。ページレコードは保留しておき、コミットレコードを読んだら、レコードの数が一致することを確かめて保留中のページを「コミット済み」とする
3. 次のいずれかで読むのをやめる: ファイルの終わり、レコードの途中でのファイルの終わり、CRC の不一致、未知のレコード種別、レコード数の不一致。それ以降と、コミットレコードのない保留中のページは **未コミットとして捨てる**
4. コミット済みのページを WAL の順に DB ファイルに書く（同じページが複数回あれば後のものが残る）。DB ファイルの長さが最後のコミットのページ数に満たなければ伸ばし、超えていれば切り詰める
5. DB ファイルを fsync し、WAL をヘッダだけに切り詰めて fsync する

- コミット済みのページが 1 つもなくても、ヘッダの後ろにデータが残っていれば WAL を切り詰める。残したままにすると、次のコミットが壊れた末尾の後ろに追記され、リカバリがその手前で止まってしまうため
- リカバリを何度繰り返しても結果は同じになる（コミット済みのページを書き直すだけなので冪等）

### チェックポイントの失敗

- WAL の fsync が終わった時点でページの dirty フラグを消す。その後のチェックポイントが I/O エラーになった場合はエラーを返すが、コミットは WAL に残っており、次に DB を開くときに反映される

### クラッシュテスト

- 環境変数 `SQLTOY_CRASH_AT` に次の地点の名前を設定すると、その地点でプロセスを即座に異常終了する（`std::process::abort`）
  - `wal-partial`: WAL にページレコードを 1 つ書いた後（コミットレコードの前）
  - `before-wal-sync`: コミットレコードを書いた後、WAL の fsync の前
  - `after-wal-sync`: WAL の fsync の後、DB ファイルへの書き込みの前
  - `mid-checkpoint`: DB ファイルにページを 1 つ書いた後
  - `before-wal-truncate`: DB ファイルの fsync の後、WAL の切り詰めの前
- 結合テストでは、この環境変数を付けて CLI のプロセスを起動して異常終了させ、別のプロセスで DB を開いて状態を確かめる
  - `after-wal-sync` 以降の地点: コミットした変更がすべて見える
  - `wal-partial`: コミットした変更は見えない（それ以前の状態）
  - `before-wal-sync`: fsync していなくても OS のキャッシュに WAL が残るため、変更は見える場合がある。「すべて見えるか、まったく見えないか」のどちらかであることを確かめる
- WAL の末尾を切り詰めたり 1 バイト書き換えたりしたファイルでも、最後の完全なコミットまでが復元されることを確かめる

## Rationale

- no-steal と組み合わせると、REDO だけで原子性と永続性を得られ、UNDO ログや LSN の管理が不要になる
- ページイメージ全体を書く物理ログは、テーブル・B+Tree・カタログのどの変更も同じ方法で扱え、リカバリが冪等になる
- コミットのたびにチェックポイントまで行うことで、WAL が大きくならず、リカバリは直前のコミットだけを考えればよい。性能より理解しやすさを優先する
- CRC とレコード数で、書きかけのレコードや壊れた末尾を検出できる

## Consequences

### Positive

- コミット済みの変更はクラッシュしても失われず、コミットの途中の変更が一部だけ残ることもない
- これまでの ADR で残していたクラッシュ時の不整合（ページの確保と初期化、行とインデックス、行の移動）が解消される

### Negative

- コミットのたびに、変更したページを WAL と DB ファイルの 2 回書き、fsync が 3 回になる
- ページの一部しか変えなくてもページ全体を WAL に書く
- DB ファイルの新規作成（ヘッダページの初期化）は WAL を通らない

## Non-goals

- 論理ログ、UNDO ログ、LSN、ARIES
- コミットとチェックポイントの分離、グループコミット
- メディア障害（ディスクの破損）からの復旧
