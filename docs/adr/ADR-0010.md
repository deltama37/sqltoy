# ADR-010: 演算子による問い合わせ実行と ORDER BY・LIMIT・JOIN を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Index の次に Query Execution を実装する。WHERE、projection、ORDER BY、LIMIT、JOIN を順次追加し、実行処理を演算子単位へ分離して、後のクエリプランナー（ステップ14）へつなげる。

WHERE と projection は ADR-0007・ADR-0008 で前倒しした。本 ADR では残りの ORDER BY、LIMIT、JOIN の構文と意味、名前解決の規則、演算子の構成を定める。

## Decision

### 構文

ADR-0007 の `select` を次のように拡張する。

```text
select      := SELECT select_item (',' select_item)*
               FROM from_item
               (WHERE expr)?
               (ORDER BY order_item (',' order_item)*)?
               (LIMIT expr (OFFSET expr)?)?
select_item := '*' | ident '.' '*' | expr (AS? ident)?
from_item   := table_ref join*
join        := (INNER)? JOIN table_ref ON expr
             | LEFT (OUTER)? JOIN table_ref ON expr
             | CROSS JOIN table_ref
             | ',' table_ref
table_ref   := ident (AS? ident)?
order_item  := expr (ASC | DESC)?
```

- キーワードに `ASC` `BY` `CROSS` `DESC` `INNER` `JOIN` `LEFT` `LIMIT` `OFFSET` `ON` `ORDER` `OUTER` を追加する
- `,` は `CROSS JOIN` と同じ意味とする
- 結合は左から順に結合する（`a JOIN b ON ... JOIN c ON ...` は `(a JOIN b) JOIN c`）

### 名前解決

- FROM の各テーブルは **束縛名**（別名があれば別名、なければテーブル名）で参照する。別名を付けたテーブルは元の名前では参照できない
- 束縛名が FROM の中で重複する場合はエラー（`duplicate table name in FROM: {name}`）とする
- 修飾なしのカラム名は、すべての束縛の中でちょうど 1 つに一致しなければならない。複数に一致すればエラー（`ambiguous column: {name}`）、どれにも一致しなければ `column not found: {name}` とする
- `t.c` は束縛名 `t` のカラム `c` を指す
- `*` はすべての束縛のカラムを FROM の順に展開し、`t.*` は束縛 `t` のカラムだけを展開する。結果のカラム名が重複してもよい
- `ON` の式から参照できるのは、その JOIN までに現れた束縛のカラムとする

### JOIN の意味

- INNER JOIN: `ON` の値が `TRUE` になる組み合わせだけを出力する
- LEFT JOIN: 左の行ごとに、`ON` が `TRUE` になる右の行がなければ、右のカラムをすべて `NULL` にした行を 1 つ出力する
- CROSS JOIN: すべての組み合わせを出力する
- `ON` の値が真偽値でも `NULL` でもない場合はエラー（`ON must be a boolean expression`）とする

### ORDER BY

- 各 `order_item` は次の順で解釈する
  1. 整数リテラルだけの式は、選択リストの位置（1 始まり）とする。範囲外ならエラー（`ORDER BY position out of range: {n}`）
  2. 修飾なしの識別子だけの式で、選択リストの別名と一致するものは、その出力の値とする
  3. それ以外は、FROM の行に対して評価する式とする
- 並べ替えは安定とし、同じキーの行は元の順序を保つ
- 値の順序は `NULL` < 真偽値 < 整数 < 文字列とし、同じ型の中では ADR-0008 の比較と同じ順とする。`NULL` は `ASC` では先頭、`DESC` では末尾になる

### LIMIT・OFFSET

- 式は行の文脈なしで評価し、0 以上の整数でなければエラー（`LIMIT must be a non-negative integer`、`OFFSET must be a non-negative integer`）とする
- ORDER BY の後に適用し、先頭から `OFFSET` 行を読み飛ばしてから最大 `LIMIT` 行を出力する

### 演算子

問い合わせは、行を 1 つずつ返す演算子の木として実行する（Volcano モデル）。各演算子は「次の行を返す」操作を持ち、行がなくなれば終わりを返す。

| 演算子 | 役割 |
| --- | --- |
| SeqScan | テーブルの行を **1 ページずつ** 読み、走査順に返す |
| IndexLookup | 主キーの B+Tree で 1 行を引く（ADR-0009） |
| Filter | 条件が `TRUE` の行だけを返す |
| NestedLoopJoin | INNER・LEFT・CROSS JOIN。右側の入力は最初に一度だけメモリに読み込む |
| Sort | 入力をすべて読んでから並べ替えて返す |
| Limit | OFFSET と LIMIT を適用する。必要な行数を返したら入力を読まない |
| Project | 選択リストの式を評価する |

- 演算子の間を流れる行は、束縛ごとの値と Record ID を持つ。LEFT JOIN で補った `NULL` の側は Record ID を持たない
- SELECT は `Scan → (Join) → Filter → Sort → Project → Limit` の順で組み立てる。ORDER BY が選択リストの別名や位置を参照する場合は、Project の結果を並べ替えに使う
- Limit が早く終われば SeqScan もそれ以上ページを読まない
- UPDATE・DELETE の対象行の決定にも同じ Scan と Filter を使う

### インデックスの利用

- ADR-0009 の規則（WHERE の `AND` の項に `pk = 定数` がある）を束縛ごとに適用し、該当する束縛の SeqScan を IndexLookup に置き換える
- ただし LEFT JOIN の右側（`NULL` を補う側）の束縛には適用しない。WHERE の条件を結合前に適用すると、`NULL` を補った行の扱いが変わるため
- これ以外の実行計画の選択はステップ14で扱う

## Rationale

- 演算子を「次の行を返す」共通の形にすることで、組み合わせて任意の問い合わせを組み立てられ、ステップ14で実行計画を差し替えられる
- SeqScan を 1 ページずつにすることで、LIMIT による早期終了の効果が読んだページ数に表れる
- JOIN の右側をメモリに読み込むことで、外側の行ごとに右のテーブルを読み直す I/O を避ける。学習用の規模では十分である
- NULL を最小とする順序は SQLite と同じで、`ASC` と `DESC` が互いに逆順になる

## Consequences

### Positive

- ORDER BY、LIMIT、INNER・LEFT・CROSS JOIN を使った問い合わせができる
- 演算子ごとに単体でテストできる

### Negative

- JOIN の右側と Sort の入力はメモリに収まる必要がある
- JOIN は入れ子ループのみで、大きなテーブルどうしの結合は遅い

## Non-goals

- RIGHT・FULL OUTER JOIN、USING、NATURAL JOIN
- 集約関数、GROUP BY、HAVING、DISTINCT、サブクエリ
- ハッシュ結合、マージ結合、外部ソート
- UPDATE・DELETE での JOIN
