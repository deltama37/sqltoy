# ADR-015: ルールベースのクエリプランナーと EXPLAIN を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、MVCC の次に Query Planner を実装する。複数の実行方法から実行計画を選択できるようにし、最初はルールベースとする。

これまで（ADR-0009、ADR-0010）の実行計画は、`pk = 定数` のときだけインデックスで 1 行を引き、それ以外はテーブル全走査・入れ子ループ結合・WHERE を結合の後で一度に適用する、という固定の形だった。本 ADR では、プランナーが選ぶ実行方法の候補、選択の規則、実行計画を確かめるための `EXPLAIN` を定める。

## Decision

### 構文

```text
statement := ... | EXPLAIN (ANALYZE)? (select | update | delete)
```

- キーワードに `EXPLAIN` と `ANALYZE` を追加する
- `EXPLAIN` は文を実行せず、実行計画を表示する
- `EXPLAIN ANALYZE` は SELECT だけに使え、文を実行したうえで、各演算子が実際に出力した行数と、読んだページ数を表示する。SELECT 以外ではエラー（`EXPLAIN ANALYZE supports only SELECT`）とする

### 実行方法の候補

アクセス方法（テーブルごと）:

| 演算子 | 内容 |
| --- | --- |
| SeqScan | テーブル全走査（ADR-0010） |
| IndexLookup | 主キーの 1 つの値を引く（ADR-0009） |
| IndexScan | 主キーの B+Tree の葉を昇順にたどる。下限・上限を持てる |

結合方法:

| 演算子 | 内容 |
| --- | --- |
| NestedLoopJoin | 右側をメモリに読み込んでの入れ子ループ（ADR-0010） |
| IndexNestedLoopJoin | 左の行ごとに、右側のテーブルを主キーのインデックスで引く |

### 選択の規則

WHERE と ON は `AND` で項に分けて扱う。ここで「定数式」はカラム参照を含まず、計画を立てる時点で評価して整数になる式とする。

1. **条件の押し下げ**: 1 つの束縛だけを参照する WHERE の項は、その束縛のアクセス方法の直上の Filter で適用する。複数の束縛を参照する項は、それらがすべてそろう最初の結合の直上で適用する。ただし LEFT JOIN の右側（`NULL` を補う側）を参照する WHERE の項は、その LEFT JOIN より上で適用する
2. **アクセス方法**: 束縛ごとに、押し下げた項のうち主キーに対する比較を見る
   - `pk = 定数式` があれば IndexLookup
   - そうでなく、`pk < 定数式`、`pk <= 定数式`、`pk > 定数式`、`pk >= 定数式`（左右が逆の形を含む）があれば、それらの共通部分を範囲とする IndexScan
   - どちらもなければ SeqScan
3. **ORDER BY の省略**: FROM がテーブル 1 つで、ORDER BY が主キーの昇順 1 つだけ（`ORDER BY pk` または `ORDER BY pk ASC`）の場合は、SeqScan の代わりに範囲なしの IndexScan を使い、Sort を省く。IndexLookup・IndexScan を選んだ場合も、出力は主キーの昇順なので Sort を省く
4. **結合方法**: INNER JOIN と LEFT JOIN で、ON の項に `右側の pk = 左側の束縛だけを参照する式` があれば、右側が主キーを持つ場合に IndexNestedLoopJoin を使う。それ以外は NestedLoopJoin とする
5. 結合の順序は FROM に書かれた順とし、入れ替えない
6. UPDATE と DELETE の対象行の決定にも、規則 1・2 を適用する

- インデックスで絞り込みに使った項も、Filter から取り除かずに評価する（範囲の境界の扱いを誤っても結果が変わらないようにするため）
- 定数式の評価がエラーになる、または整数にならない項は、インデックスの選択に使わない（ADR-0009 と同じく、エラーや結果を全走査と同じにするため）

### MVCC との関係

- IndexLookup と IndexScan は、範囲内のすべてのエントリ（バージョン）を引き、ADR-0014 の可視性の規則で見えるものだけを返す

### EXPLAIN の表示

結果は 1 カラム `QUERY PLAN` の行の並びとし、各行が演算子 1 つを表す。子の演算子は 2 文字ずつ字下げする。

```text
 QUERY PLAN
----------------------------------------------
 Limit 10
   Project u.name, o.item
     IndexNestedLoopJoin inner orders AS o (o.id = u.last_order)
       Filter (u.id >= 3)
         IndexScan users AS u (id >= 3)
(5 rows)
```

- 各演算子の表示: `SeqScan {table}`、`IndexLookup {table} ({pk} = {値})`、`IndexScan {table}`（範囲があれば `({pk} >= {値} AND {pk} < {値})` の形で付ける）、`Filter ({式})`、`NestedLoopJoin {inner|left|cross}`、`IndexNestedLoopJoin {inner|left} {table} ({pk} = {式})`、`Sort {キー}`、`Project {式}`、`Limit {n}`（OFFSET があれば ` OFFSET {m}`）。別名のある束縛は `{table} AS {alias}` とする。式は ADR-0007 の `Display` の形とする
- `EXPLAIN ANALYZE` では各行の末尾に ` (rows={n})` を付け、最後の行を `Pages read: {n}` とする

### プランナーの無効化

- 比較のために、`Database` にプランナーを無効にする操作を設ける。無効のときは、すべての束縛を SeqScan で読み、NestedLoopJoin で結合し、WHERE を結合の後で一度に適用し、ORDER BY は Sort で行う
- プランナーが有効でも無効でも結果が同じになることを、ランダムに生成した問い合わせでテストする

## Rationale

- ルールベースは、どの条件でどの実行方法になるかが明確で、EXPLAIN と合わせて学習しやすい
- 押し下げとインデックスの利用は、統計情報がなくても常に読み込むページ数を減らす方向に働く。順序の入れ替えやコストの比較が必要になる判断（結合順序など）は扱わない
- 主キーの順に葉をたどる IndexScan は、範囲検索と ORDER BY の省略の両方に使える。LIMIT と組み合わせれば、先頭の数行だけを読んで終われる
- プランナーを無効にした実行と比べるテストは、規則の追加によって結果が変わっていないことを広く確かめられる

## Consequences

### Positive

- 主キーの範囲検索、主キー順の ORDER BY ... LIMIT、主キーでの結合が、テーブル全走査なしに実行できる
- EXPLAIN で実行計画を、EXPLAIN ANALYZE で実際の行数と読んだページ数を確かめられる

### Negative

- 統計情報を使わないため、インデックスを使うほうが遅い場合（範囲がテーブルのほとんどを含む場合など）も IndexScan を選ぶ
- 結合の順序は書いた順のままで、よりよい順序を選ばない

## Non-goals

- 統計情報、コストベースの選択、結合順序の最適化
- 降順の IndexScan、二次インデックス
- ハッシュ結合、マージ結合
- EXPLAIN ANALYZE の UPDATE・DELETE 対応
