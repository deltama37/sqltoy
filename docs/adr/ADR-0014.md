# ADR-014: MVCC による複数トランザクションの扱いを定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、WAL / Recovery の次に MVCC を実装する。複数トランザクションを扱うための MVCC を導入し、Transaction ID、row version、visibility、snapshot、rollback を扱う。

これまでの実装（ADR-0012）では、トランザクションは同時に 1 つだけで、ロールバックはバッファプールの dirty なページを捨てることで行っていた。複数のトランザクションが同じページを共有すると、この方式では他のトランザクションの変更まで捨ててしまう。また sqltoy は 1 つのプロセスで動き、スレッドも使わない。

本 ADR では、1 つのプロセスの中で複数のトランザクションを交互に実行する仕組み、行のバージョンの形式、可視性の規則、書き込みの競合、ロールバックとクラッシュ後の後始末、不要になったバージョンの回収を定める。

## Decision

### セッション

- `Database` は複数の **セッション** を持てる。各セッションは同時に高々 1 つのトランザクションを持つ（ADR-0012 の規則はセッションごとに適用する）
- 文は 1 つずつ最後まで実行する。複数のセッションの文が同時に実行されることはなく、セッションを切り替えながら交互に実行する
- これまでの API（`execute` など）は既定のセッションで実行する
- REPL に `.session {name}` を追加し、名前付きのセッションに切り替える（なければ作る）。既定のセッションの名前は `main` とする。端末ではプロンプトにセッション名を含める（`main` 以外のとき `sqltoy:{name}> `）
- セッションを閉じる（REPL の終了を含む）と、開いているトランザクションはロールバックする

### Transaction ID

- トランザクションは開始時に、単調に増える 64 ビットの **Transaction ID**（`xid`）を受け取る。`0` は「なし」を表す
- 次に割り当てる xid をヘッダページのオフセット 16 に `u64` で保存する。flush のたびにその時点の値を書き込むので、ディスク上の行に現れる xid はいつも保存値より小さい
- 自動コミットの文も、その文だけのトランザクションとして xid を受け取る

### 行のバージョン

ADR-0006 の行のバイト列の前に、次の **バージョンヘッダ**（17 バイト）を付けたものをレコードとする。

| サイズ | 内容 |
| --- | --- |
| 8 | `xmin`: このバージョンを作ったトランザクションの xid（`u64`） |
| 8 | `xmax`: このバージョンを削除したトランザクションの xid（`u64`、なければ `0`） |
| 1 | フラグ: bit 0 = `xmin` がコミット済み、bit 1 = `xmax` がコミット済み |

- INSERT は `xmin` = 自分の xid の新しいバージョンを作る
- DELETE は見えているバージョンの `xmax` に自分の xid を書く
- UPDATE は古いバージョンを DELETE と同じく削除し、新しい値のバージョンを INSERT と同じく作る。**行をその場で書き換えることはない**
- ヘッダページのフォーマットバージョンを **`4`** に上げる

### スナップショットと可視性

- トランザクションは開始時に **スナップショット** を取る。スナップショットは「次に割り当てる xid」（上限）と、その時点で実行中の他のトランザクションの xid の集合を持つ（明示的なトランザクションは `BEGIN` の時点、自動コミットは文の開始時点）
- バージョンの `xmin`（または `xmax`）がスナップショット `S` で **コミット済みに見える** とは、その xid が `S` の上限より小さく、`S` の実行中の集合に含まれず、バージョンの対応するコミットフラグが立っていることとする
- トランザクション `T` からバージョン `v` が見えるのは、次の両方を満たすときとする
  - `v.xmin` が `T` 自身であるか、`T` のスナップショットでコミット済みに見える
  - `v.xmax` が `0` であるか、`T` 自身でもなく、`T` のスナップショットでコミット済みにも見えない
- この規則により、分離レベルは **スナップショット分離** になる。ダーティリード、ノンリピータブルリード、ファントムは起きない。write skew は起こりうる

### コミットとロールバック

- 各トランザクションは、作ったバージョンと `xmax` を書いたバージョンの一覧（書き込み集合）を持つ
- コミット: 書き込み集合のバージョンにコミットフラグ（作ったものは bit 0、削除したものは bit 1）を立て、ADR-0013 の手順で flush する
- 何も書き込まなかったトランザクション（SELECT だけのものなど）のコミットでは、ヘッダページも含めて何も書かない。その xid はディスク上に現れないので、保存した「次の xid」を進めなくてよい
- ロールバック: 書き込み集合を逆順にたどり、作ったバージョンは削除し（インデックスのエントリも取り除く）、`xmax` を書いたバージョンは `xmax` を `0` に戻す。その後 flush する
- これにより、コミットもロールバックもしていないトランザクションのバージョンだけが、フラグのない状態で存在する
- 文のロールバック（ADR-0012 のセーブポイント）はこれまでどおりとし、あわせて書き込み集合をその文の前の状態に戻す
- dirty なページを追い出さない規則（ADR-0012）は保つ。ただし flush は他のセッションの未コミットの変更を含むページも書く。そのページには文の途中の状態は含まれない（文の境界でしか flush しないため）

### 書き込みの競合

単一スレッドなので待ち合わせは行わず、競合はエラーにする（first-updater-wins）。

- 更新・削除しようとしたバージョンの `xmax` が、他の実行中のトランザクションか、スナップショットの後にコミットしたトランザクションの xid であれば、エラー（`serialization failure: row was modified by a concurrent transaction`）とする
- エラーになった文はロールバックされ、トランザクションは続く。利用者は ROLLBACK してやり直す

### 主キーとインデックス

- B+Tree のエントリを **（キー, Record ID）の組** で順序付けし、同じキーのエントリを複数持てるようにする。1 つのエントリは 1 つのバージョンを指す
- 内部ノードのエントリは「区切りキー（8）+ 区切りの Page ID（4）+ Slot ID（2）+ 子の Page ID（4）」の 18 バイトとし、最大キー数を `(4096 - 16) / 18 = 226` とする。葉の形式は ADR-0009 と同じとする
- 主キーの検索は、そのキーのエントリをすべてたどり、見えるバージョンを返す
- INSERT と、主キーを変える UPDATE の一意性検査では、そのキーの各バージョンについて次のように判定する
  - 削除済み（`xmax` が自分か、自分のスナップショットでコミット済みに見える）のバージョンは無視する
  - 自分のスナップショットからは見えるが、スナップショットの後に削除がコミットされたバージョンがあれば serialization failure とする（キーを再利用すると、同じキーの行が 2 つ見えてしまうため）
  - 他の実行中のトランザクションが作ったか削除中のバージョンがあれば serialization failure とする
  - それ以外（コミット済みで削除されていないもの、自分が作ったもの）があれば `duplicate primary key` とする
- バージョンの削除（`xmax` の設定）ではインデックスのエントリを残す。古いスナップショットから引けるようにするため

### クラッシュ後の後始末

- flush のとき、他の実行中のトランザクションが書き込みを持っていれば、ヘッダページのオフセット 24 の **後始末フラグ**（`u8`）を `1` にし、なければ `0` にする
- DB を開くとき、リカバリ（ADR-0013）の後で後始末フラグが `1` なら、全テーブルを走査し、`xmin` のフラグがないバージョンを削除し（インデックスのエントリも取り除く）、`xmax` のフラグがないバージョンの `xmax` を `0` に戻す。その後フラグを `0` にして flush する

### VACUUM

- 文 `VACUUM` を追加する（キーワード `VACUUM`）。結果の表示は `VACUUM {n}`（取り除いたバージョンの数）とする
- `xmax` がコミット済みで、実行中のどのトランザクションのスナップショットでもコミット済みに見えるバージョンを、すべてのテーブルから物理的に削除し、インデックスのエントリも取り除く
- 明示的なトランザクションの中では実行できない（`VACUUM cannot run inside a transaction`）

### カタログ

- テーブルの定義はバージョン管理しない。CREATE TABLE は、コミット前でも他のセッションから見える
- 他のセッションにトランザクションがあるときの CREATE TABLE はエラー（`CREATE TABLE requires no other active transactions`）とする
- CREATE TABLE を含むトランザクションをロールバックすると、行を取り消した後でカタログのレコードを削除する。そのテーブルのページは空のまま残る

## Rationale

- セッションを交互に実行する形にすることで、スレッドやロックなしに、複数トランザクションの可視性と競合を確かめられる
- コミット時にバージョンへフラグを立てる方式（PostgreSQL のヒントビットに近い）にすることで、トランザクションの状態を別のファイル（コミットログ）に保存しなくてよい。コミットしたトランザクションのバージョンには必ずフラグがあり、ロールバックしたトランザクションのバージョンは残らない
- ロールバックを書き込み集合による論理的な取り消しにすることで、他のトランザクションの変更を巻き込まずに取り消せる。クラッシュで失われたトランザクションの取り消しは、フラグのないバージョンとして DB ファイルから判別できるので、UNDO ログが不要である
- インデックスのエントリを（キー, Record ID）で一意にすることで、PostgreSQL と同じく、インデックスからは全バージョンを引き、可視性はテーブル側で判定できる

## Consequences

### Positive

- 複数のトランザクションが互いの未コミットの変更を見ずに実行できる
- 読み出しが書き込みを妨げず、書き込みも読み出しを妨げない

### Negative

- UPDATE と DELETE のたびに古いバージョンが残り、VACUUM するまでテーブルとインデックスが大きくなる
- 行ごとに 17 バイトのヘッダが増える
- コミットは書き込み集合の全バージョンにフラグを書くため、書いたページをもう一度書き換える
- CREATE TABLE はトランザクション分離の対象外で、ロールバックしても空のページが残る
- フォーマットバージョンを上げるため、これまでのファイルは開けない

## Non-goals

- スレッドやプロセスをまたいだ並行実行、ロック、待ち合わせ
- Serializable（SSI）、Read Committed など他の分離レベル
- 自動 VACUUM、xid の周回（wraparound）
