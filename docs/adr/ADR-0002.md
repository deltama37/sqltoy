# ADR-002: sqltoy の実装順序を定める

## Status

Accepted

## Context

sqltoy はRDBMSの主要な構成要素を自ら実装して理解することを目的としている。

RDBMSはストレージ、インデックス、SQL実行、トランザクションなど複数の層から構成されるため、依存関係を無視して実装すると設計変更や作り直しが増えやすい。

そのため、下位層から段階的に実装し、各段階で動作確認できる順序を定める。

## Decision

以下の順序で実装する。

### 1. Storage

ローカルファイルをバイト列として読み書きできる最小のストレージ層を作る。

完成条件:

- DBファイルを作成できる
- 任意位置のデータを読み書きできる
- 再起動後もデータが残る

### 2. Page Manager

DBファイルを固定長ページとして扱えるようにする。

完成条件:

- Page IDからページを取得できる
- 新しいページを確保できる
- ページを変更して永続化できる

この段階でページサイズと基本的なページ形式を決める。

### 3. Record Storage

ページ内にレコードを格納できるようにする。

可変長レコードを扱える構造を採用する。

完成条件:

- レコードを追加できる
- Record IDから取得できる
- レコードを削除・更新できる
- 複数ページにレコードを格納できる

### 4. Catalog

テーブルやカラムなどのスキーマ情報をDB内部に保持する。

完成条件:

- テーブルを作成できる
- テーブル定義を永続化できる
- 再起動後にスキーマを復元できる

この段階まではSQLを必要としない内部APIで実装する。

### 5. Table Operations

スキーマを利用して行を操作できるようにする。

完成条件:

- INSERT
- 全件走査
- UPDATE
- DELETE

を内部APIから実行できる。

### 6. SQL Parser

必要最小限のSQLを構文解析できるようにする。

初期対象:

```sql
CREATE TABLE
INSERT
SELECT
UPDATE
DELETE
```

構文解析結果はASTとして表現する。

### 7. Executor

ASTを実際のテーブル操作へ変換する。

完成条件:

```sql
CREATE TABLE users (
    id INTEGER,
    name TEXT
);

INSERT INTO users VALUES (1, 'Alice');

SELECT * FROM users;
```

がCLIから実行できる。

ここを最初のRDBとしてのマイルストーンとする。

### 8. Index

B+Treeインデックスを実装する。

最初は主キー検索のみを対象とする。

完成条件:

```sql
SELECT *
FROM users
WHERE id = 1;
```

をテーブル全走査せず取得できる。

### 9. Query Execution

問い合わせ処理を拡張する。

順次以下を追加する。

- WHERE
- projection
- ORDER BY
- LIMIT
- JOIN

実行処理を演算子単位へ分離し、後のクエリプランナーへつなげる。

### 10. Buffer Pool

ページ読み書きのたびにファイルアクセスしないよう、ページキャッシュを導入する。

完成条件:

- ページをメモリ上に保持できる
- dirty pageを管理できる
- evictionできる
- 必要なページを永続化できる

### 11. Transaction

単一トランザクションから開始し、トランザクション境界を導入する。

```sql
BEGIN;
...
COMMIT;
```

この段階では高度な並行実行は扱わない。

### 12. WAL / Recovery

Write-Ahead Loggingを導入する。

完成条件:

- commit済みの変更をクラッシュ後に復元できる
- 未commitの変更を復元時に適切に処理できる

意図的にプロセスを停止させるクラッシュテストを追加する。

### 13. MVCC

複数トランザクションを扱うためのMVCCを導入する。

以下を扱う。

- Transaction ID
- row version
- visibility
- snapshot
- rollback

### 14. Query Planner

複数の実行方法から実行計画を選択できるようにする。

最初はルールベースとし、必要に応じて統計情報とコストベースの判断を追加する。

例:

```text
Seq Scan

vs

Index Scan
```

## Development Rule

各段階では、その層の公開インターフェースとテストを完成させてから次へ進む。

上位層の都合だけを理由に未実装の下位層へ機能を追加しない。

実装中に新しい設計判断が必要になった場合のみ、追加のADRを作成する。

例えば以下。

- ページサイズ
- slotted pageの形式
- B+Treeのノード構造
- WAL形式
- MVCC方式

実装順そのものについては、本ADRを基準とする。

## Consequences

### Positive

- 常に動作する小さなDBを維持しながら進められる
- RDBMSの各層の依存関係を順番に理解できる
- SQL実装だけに偏らず、ストレージから学習できる
- 実装対象を迷いにくくなる

### Negative

- SQLを実際に入力して動かせるようになるまで一定の実装量が必要になる
- 後の実装によって下位層の設計変更が必要になる可能性がある
- 一般的なRDBMSと完全に同じ実装順になるとは限らない
