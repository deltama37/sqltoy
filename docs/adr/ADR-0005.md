# ADR-005: テーブルごとのページ管理とカタログ形式を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Record Storage の次に Catalog を実装する。

Catalog は、テーブルやカラムなどのスキーマ情報を DB ファイル内部に保持し、再起動後に復元できるようにする層である。

ADR-0004 では、Catalog が存在しない段階の最小構成として、DB ファイル内のデータページ全体を1つのレコード集合として扱い、テーブルごとのページ管理は Catalog で改めて決めるとした。

本 ADR では次の2点を定める。

- どのページがどのテーブルのレコードを持つかを表す方法
- スキーマ情報の格納場所と符号化形式

行の値の符号化（カラム型ごとのシリアライズ）は Table Operations（ステップ5）で扱う。

## Decision

### テーブル ID とページの所有者

- テーブルは **テーブル ID**（`u16`）で識別する
- レコードページは、ちょうど1つのテーブルに属する
- 所有者のテーブル ID は、ADR-0004 のページヘッダで予約としていたオフセット 6 の 2 バイトに格納する

ページヘッダ（8 バイト、リトルエンディアン）:

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 1 | ページ種別（`u8`、レコードページは `1`） |
| 1 | 1 | 予約（ゼロ） |
| 2 | 2 | スロット数 `slot_count`（`u16`） |
| 4 | 2 | レコード領域の開始位置 `free_end`（`u16`） |
| 6 | 2 | **所有者のテーブル ID**（`u16`） |

テーブル ID の割り当て:

| テーブル ID | 用途 |
| --- | --- |
| 0 | 使用しない（不正） |
| 1 | カタログ（システムテーブル） |
| 2 以降 | ユーザーテーブル（作成順に割り当てる） |

### Record Storage の変更

ADR-0004 の規則を、テーブル単位に読み替える。

- 追加: Page 1 から順に走査し、**所有者が同じテーブル**でレコードを格納できる最初のページに追加する。なければ新しいページを確保し、そのテーブルの所有として初期化する
- 走査: 所有者が同じテーブルのページだけを、ページ順・スロット順に返す
- 取得・更新・削除: Record ID の指すページの所有者が指定テーブルと異なる場合は「レコードが存在しない」エラーとする
- 所有者が 0 のレコードページは不正なページ（`InvalidData`）とする

Record ID の形式（`page_id:slot_id`）は変えない。Record ID は DB ファイル全体で一意である。

### カタログ

カタログは、テーブル ID 1 のレコード集合として保持する。1 テーブルにつき 1 レコードとする。

カタログレコードの形式（リトルエンディアン）:

| サイズ | 内容 |
| --- | --- |
| 2 | テーブル ID（`u16`） |
| 2 + n | テーブル名（長さ `u16` + UTF-8 バイト列） |
| 2 | カラム数（`u16`） |
| カラムごとに 2 + n | カラム名（長さ `u16` + UTF-8 バイト列） |
| カラムごとに 1 | カラム型（`u8`） |

カラムは定義順に並べ、カラムごとに「カラム名、カラム型」の順で連続して置く。

カラム型:

| 値 | 型 | 意味 |
| --- | --- | --- |
| 1 | `INTEGER` | 64 bit 符号付き整数 |
| 2 | `TEXT` | UTF-8 文字列 |

- カタログレコードが ADR-0004 の最大長（4084 バイト）を超える定義はエラーとする

### 名前の規則

- テーブル名とカラム名は、ASCII の英字または `_` で始まり、英数字または `_` が続く 1〜64 バイトの識別子とする
- 名前は定義時の綴りのまま保存する
- 名前の比較は ASCII の大文字・小文字を区別しない（`users` と `Users` は同じテーブル）
- テーブル名は DB 内で一意、カラム名はテーブル内で一意とする
- テーブルは 1 つ以上のカラムを持つ

### テーブルの作成と復元

- テーブル作成時は、名前の規則と重複を検査し、既存の最大テーブル ID + 1（ユーザーテーブルがなければ 2）を割り当て、カタログレコードを追加して fsync する
- DB を開くときにカタログを走査し、全テーブルのスキーマをメモリに読み込む
- カタログレコードが壊れている（形式が読めない、テーブル ID が重複している、未知のカラム型など）場合は `InvalidData` とする

### フォーマットバージョン

- ヘッダページのフォーマットバージョンを **`2`** に上げる
- ADR-0004 の形式のファイルは所有者が 0 のページを持ち、本形式とは互換性がない
- Page Manager は、フォーマットバージョンが `2` 以外のファイルを開くときにエラーとする。学習用プロジェクトであり、保持すべき既存データがないため、旧形式からの移行は行わない

### 公開インターフェース

Record Storage の上に構築し、少なくとも以下を提供する。

- DB ファイルを開き、カタログを読み込む
- テーブル名とカラム定義を指定してテーブルを作成する
- テーブル名からスキーマ（テーブル ID、名前、カラムの名前と型）を引く
- 全テーブルのスキーマを作成順に列挙する

この段階では SQL を使わず、内部 API と CLI から操作する。

## Rationale

- 所有者のテーブル ID をページヘッダの予約領域に置くことで、ADR-0004 のレイアウトを動かさずにテーブルを区別できる
- ページを所有者で区別するだけの方式は、テーブルごとのページ連結リストより単純で、ページの確保と初期化の手順も ADR-0004 から変わらない
- カタログを通常のレコード集合として持つことで、スキーマの永続化に Record Storage をそのまま使える（SQLite の `sqlite_schema` と同じ考え方）
- 型は ADR-0002 の目標の SQL（`INTEGER`、`TEXT`）に必要な最小限に絞る
- 行の値の符号化はここで決めず、NULL の扱いなどと合わせてステップ5で決める

## Consequences

### Positive

- 複数のテーブルを1つの DB ファイルに格納できる
- 再起動後もスキーマを復元できる
- カタログ自体も Record Storage のテストで検証済みの仕組みに載る

### Negative

- テーブルの追加・走査では、他のテーブルのページも含めて全ページを読む。ページ数に比例して遅くなる
- テーブル ID が `u16` のため、テーブル数は約 65,000 に限られる
- フォーマットバージョンを上げるため、ADR-0004 の形式で作ったファイルは開けなくなる

## Non-goals

- 行の値の符号化（ステップ5で扱う）
- DROP TABLE、ALTER TABLE、テーブル名の変更
- 主キー・NOT NULL などの制約（主キーはステップ8のインデックスと合わせて扱う）
- `INTEGER` と `TEXT` 以外の型
- テーブルごとのページ連結リストや free space map
