# ADR-006: 行の符号化とテーブル操作を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Catalog の次に Table Operations を実装する。

Table Operations は、Catalog のスキーマを使って行を操作する層である。完成条件は、INSERT・全件走査・UPDATE・DELETE を内部 API から実行できることである。

ADR-0005 では、行の値の符号化（カラム型ごとのシリアライズ）と NULL の扱いをこのステップに委ねた。本 ADR でそれらと、テーブル操作の規則を定める。

## Decision

### 値

行の値は次のいずれかとする。

| 値 | 入れられるカラム型 |
| --- | --- |
| `NULL` | すべての型 |
| 整数（`i64`） | `INTEGER` |
| 文字列（UTF-8） | `TEXT` |

- すべてのカラムは NULL を許す（NOT NULL 制約は扱わない）
- 型の暗黙変換は行わない。整数を `TEXT` カラムに、文字列を `INTEGER` カラムに入れるとエラーとする

### 行の形式

1 行を 1 レコードとして、そのテーブルのレコード集合（ADR-0005）に格納する。

レコードの内容は、NULL ビットマップと、NULL でない値の並びで構成する（リトルエンディアン）。

| サイズ | 内容 |
| --- | --- |
| ⌈カラム数 / 8⌉ | NULL ビットマップ |
| 可変 | NULL でない値を、カラムの定義順に連続して置く |

- NULL ビットマップでは、カラム `i` をバイト `i / 8` のビット `i % 8`（最下位ビットが 0）で表し、1 なら NULL とする
- カラム数は行に持たず、スキーマから求める
- 値の符号化:

| 型 | 符号化 |
| --- | --- |
| `INTEGER` | 8 バイトの `i64` |
| `TEXT` | 長さ（`u16`）+ UTF-8 バイト列 |

- 行を復号するときは、スキーマに従って読み、バイト列をちょうど使い切ることを確かめる。読めない場合は `InvalidData` とする

### テーブル操作

テーブルはテーブル名（ADR-0005 の規則で、大文字・小文字を区別しない）で指定する。存在しないテーブルはエラーとする。

- INSERT: 値の個数がカラム数と一致し、各値が型に合うことを確かめてから行を追加し、Record ID を返す
- 全件走査: テーブルの全行を、Record ID とともに ADR-0005 の走査順で返す
- UPDATE: Record ID と新しい値の並びを受け取り、行全体を置き換える。値の検査は INSERT と同じ
- DELETE: Record ID の行を削除する

UPDATE で行が大きくなり同じページに収まらない場合は、**新しい行を別の位置に追加してから古い行を削除し、新しい Record ID を返す**。収まる場合は Record ID を変えない。

- ADR-0004 は Record Storage の更新で Record ID を変えないと定めており、その規則は変えない。移動はテーブル操作の層で、追加と削除の組み合わせとして行う
- 追加を先に行うため、その間でクラッシュすると同じ行が2つ残る可能性がある。クラッシュ時の整合性は WAL / Recovery（ステップ12）で扱う

行の符号化後の長さが ADR-0004 の最大長（4084 バイト）を超える場合はエラーとする。

### 公開インターフェース

Catalog の `Database` に、少なくとも以下を追加する。

- テーブル名と値の並びを指定して行を追加する
- テーブル名を指定して全行を走査する
- テーブル名・Record ID・値の並びを指定して行を更新し、更新後の Record ID を返す
- テーブル名・Record ID を指定して行を削除する

条件付きの UPDATE・DELETE は、走査と Record ID 指定の操作を組み合わせて上位層（Executor）で実現する。

## Rationale

- NULL ビットマップにより、NULL の値はバイトを消費せず、型ごとの「NULL を表す特別な値」も不要になる
- カラム数を行に持たないことで行が小さくなる。ALTER TABLE を扱わないため、スキーマと行の形は常に一致する
- `TEXT` の長さを `u16` にしても、レコードの最大長（4084 バイト）の範囲を十分に表せる
- UPDATE で行が大きくなる場合に失敗させると、SQL の UPDATE がページの空き具合という利用者に見えない事情で失敗する。テーブル操作の層で移動させることでそれを避け、Record Storage の規則は保つ
- 条件付き操作をこの層に入れないことで、WHERE の評価は Executor と Query Execution（ステップ7・9）にまとめられる

## Consequences

### Positive

- スキーマに従って型付きの行を格納・取得できる
- NULL を扱える
- UPDATE が同じページの空き具合に左右されずに成功する

### Negative

- UPDATE で Record ID が変わることがある。Record ID を保持する上位層（将来のインデックスなど）は、UPDATE の戻り値で更新する必要がある
- UPDATE の移動中にクラッシュすると、同じ行が重複する可能性がある
- カラム数を行に持たないため、ALTER TABLE ADD COLUMN を導入するときは行の形式を見直す必要がある

## Non-goals

- NOT NULL・主キー・一意性などの制約
- 型の暗黙変換
- 条件付きの UPDATE・DELETE（Executor で扱う）
- 1 ページに収まらない大きな行
- ALTER TABLE
