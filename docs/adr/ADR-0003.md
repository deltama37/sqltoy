# ADR-003: ページサイズと基本的なページ形式を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Storage 層の次に Page Manager を実装する。

Page Manager は、ローカルファイルを固定長の「ページ」の列として扱い、Page ID を使ってページの取得・確保・永続化を行う層である。

ADR-0002 の Development Rule では、ページサイズやページ形式のような設計判断が必要になった場合は追加の ADR を作成すると定めている。本 ADR でそれらを定める。

この段階ではまだレコードの格納形式（slotted page）は扱わない。レコード管理は ADR-0002 のステップ3で導入する。本 ADR の対象は、あくまで「ファイルをページ単位で管理するための最小限の取り決め」である。

## Decision

### ページサイズ

ページサイズは **4096 バイト（4 KiB）固定**とする。

- 多くの OS のメモリページ・ブロックサイズと一致し、I/O 効率がよい
- SQLite などの既存 RDBMS の既定値とも揃っており、学習時の比較がしやすい
- 当面は可変にせず、コンパイル時定数 `PAGE_SIZE = 4096` として扱う

### ページの扱い

- DB ファイルは常にページサイズの整数倍の長さを持つ、固定長ページの列として扱う
- 各ページは先頭から 0 始まりの **Page ID** で識別する
- Page ID は 32bit 符号なし整数（`u32`）で表現する
- ページのファイル内オフセットは `page_id * PAGE_SIZE` で求める

### ヘッダページ（基本的なページ形式）

ファイルを自己記述的にするため、**Page 0 をデータベースヘッダページ**として予約する。

ヘッダページの先頭に、リトルエンディアンで以下を格納する。残りはゼロ埋めとする。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 8 | マジックバイト列 `b"SQLTOYDB"` |
| 8 | 4 | フォーマットバージョン（`u32`、初期値 `1`） |
| 12 | 4 | ページサイズ（`u32`、初期値 `4096`） |
| 16 | - | 予約（ゼロ） |

- 整数のバイト順は、ファイル全体を通じて**リトルエンディアン**に統一する
- 新規ファイルを開いたときはヘッダページを初期化する
- 既存ファイルを開いたときはマジックとページサイズを検証し、一致しなければエラーとする

### Page Manager の公開インターフェース

Storage 層（ADR-0002 ステップ1）の上に構築し、少なくとも以下を提供する。

- 新規／既存ファイルを開く（新規時はヘッダページを初期化、既存時は検証）
- 現在のページ数を返す
- 新しいページを確保する（末尾にゼロ埋めページを追加し、その Page ID を返す）
- Page ID からページを読み出す
- ページを書き戻す
- 永続化（fsync）する

データページの確保は当面「末尾への追加のみ」とし、解放済みページの再利用（フリーリスト）は扱わない。

## Rationale

- ページサイズを固定することで、オフセット計算と I/O 境界が単純になり、学習時の見通しがよい
- ヘッダページを設けることで、ファイルが自己記述的になり、将来のフォーマット変更時にバージョン判定ができる
- バイト順を一か所に統一して定めておくことで、後続の Record / Index / WAL 層での表現揺れを防ぐ

## Consequences

### Positive

- ファイルがページ単位で一貫して扱えるようになり、以降の Record Storage を載せる土台ができる
- ヘッダによりファイル破損や非対応フォーマットを早期に検出できる
- Page ID という上位層共通の抽象ができる

### Negative

- ヘッダページ（Page 0）の分だけ、データページは Page ID 1 以降となる
- フリーリストが無いため、削除後のページ再利用は後続の課題として残る
- ページサイズ固定のため、巨大レコードやサイズ最適化は本段階では扱えない

## Non-goals

- slotted page などレコード格納形式の決定（ADR-0002 ステップ3で扱う）
- フリーリストやページ再利用
- バッファプール／ページキャッシュ（ADR-0002 ステップ10で扱う）
- ページサイズの可変化・実行時設定
