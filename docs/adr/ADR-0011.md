# ADR-011: バッファプールの構成と書き出しの規則を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Query Execution の次に Buffer Pool を実装する。ページの読み書きのたびにファイルにアクセスしないよう、ページキャッシュを導入する。

完成条件は次のとおりである。

- ページをメモリ上に保持できる
- dirty page を管理できる
- eviction できる
- 必要なページを永続化できる

これまでは Record Storage と B+Tree が、操作のたびに変更したページを書き込んで fsync していた（ADR-0004）。バッファプールを入れると、書き込みをいつディスクへ反映するかを改めて決める必要がある。

## Decision

### 位置づけ

- バッファプールを Page Manager（ADR-0003）と、その上の層（Record Storage、B+Tree、Catalog）の間に置く
- 上の層は Page Manager を直接使わず、バッファプールを通してページを読み書きする
- バッファプールの操作は Page Manager と同じ形にする: ページ数、ページの確保、読み出し、書き込み、永続化（flush）

### フレーム

- バッファプールは固定数の **フレーム** を持ち、各フレームは 1 ページの内容、Page ID、dirty フラグ、最終使用時刻を持つ
- フレーム数の既定値は 256（1 MiB）とし、DB を開くときに変えられるようにする。最小は 1 とする
- 読み出しはフレームの内容の複製を返し、書き込みは内容をフレームに複製する。上の層がフレームを直接借りることはないので、ピン留めは行わない

### 読み出しと書き込み

- 読み出し: 対象のページがフレームにあればそれを返す（ヒット）。なければディスクから読み、フレームに入れてから返す（ミス）
- 書き込み: フレームの内容を置き換えて dirty にする。ディスクにはすぐには書かない。フレームになければ、ディスクから読まずに新しいフレームを割り当てる
- ページの確保: ディスクには書かず、ゼロ埋めのページを dirty なフレームとして作る。ページ数はバッファプールが管理し、ファイル上のページ数と、まだ書き出していない新しいページの数の合計とする

### eviction

- 空きフレームがないときは、**最終使用時刻が最も古いフレーム**（LRU）を追い出す
- 追い出すフレームが dirty なら、先にそのページをディスクに書く（fsync はしない）

### flush（永続化）

- flush は、dirty なページを **Page ID の昇順に** すべてディスクに書いてから fsync し、dirty フラグを消す
- ファイルの末尾より後ろのページを書くとファイルが伸びる。昇順に書くことで、途中に書かれていないページが残らないようにする

### 永続化の単位

- Record Storage と B+Tree は、操作ごとに fsync しない
- **SQL の 1 文の実行が終わったときに flush する**。`Database` の行操作 API（ADR-0006 の insert・update・delete）とテーブル作成も、それぞれの終わりに flush する
- 文の実行がエラーで終わった場合も、それまでの変更を flush する（ADR-0008 の「文が途中まで適用されることがある」という性質はこれまでと同じ。ステップ11で扱う）

### 統計

- バッファプールは次を数え、`Database` から参照できるようにする: 論理的な読み出し回数、ヒット数、ミス数（ディスクからの読み出し回数）、ディスクへの書き込みページ数、eviction 数
- ADR-0009 の「読み込んだページ数」は論理的な読み出し回数とする（インデックスの効果はバッファの状態に左右されずに確かめられる）
- REPL に `.stats` コマンドを追加し、これらの値を表示する

## Rationale

- Page Manager と同じ形の操作にすることで、上の層の変更を「何を通して読み書きするか」の置き換えだけにできる
- 複製を返す方式は 4 KiB のメモリコピーが増えるが、Rust の借用規則とピン留めの管理を避けられ、単一スレッドの学習用実装として単純である
- LRU は理解しやすく、フレーム数が小さいので最も古いフレームの探索は線形でよい
- 永続化の単位を文にすることで、1 文の中で同じページを何度変更してもディスクへの書き込みは 1 回で済む。これはステップ11でトランザクションの境界に置き換える前提である

## Consequences

### Positive

- 同じページを繰り返し読む処理（JOIN、B+Tree の探索、UPDATE）でディスクの読み出しが減る
- 1 文の中の書き込みがまとめられ、fsync の回数が文ごとに 1 回になる

### Negative

- flush が複数のページを書く途中でクラッシュすると、文の変更の一部だけがディスクに残る（ステップ12で扱う）
- 追い出しによって、flush の前に dirty なページがディスクに書かれることがある
- ページの内容をフレームと上の層の間で複製するコストがかかる

## Non-goals

- 複数スレッドからの同時アクセス、ピン留め、ラッチ
- Clock や LRU-K などの置き換え方式
- 先読み
