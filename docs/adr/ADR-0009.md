# ADR-009: 主キーと B+Tree インデックスの形式を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Executor の次に Index を実装する。B+Tree インデックスを作り、最初は主キー検索のみを対象とする。

完成条件は次の SQL をテーブル全走査せずに取得できることである。

```sql
SELECT * FROM users WHERE id = 1;
```

これまでのスキーマには主キーがない（ADR-0005 の Non-goals）。本 ADR では主キーの構文と意味、B+Tree ノードのページ形式、インデックスの保守、インデックスを使う条件を定める。

## Decision

### 主キー

構文（ADR-0007 の `column_def` を拡張する）:

```text
column_def := ident type (PRIMARY KEY)?
```

- キーワードに `PRIMARY` と `KEY` を追加する
- 主キーはテーブルにつき最大 1 カラムで、型は `INTEGER` に限る。2 つ以上の指定や `TEXT` の主キーはエラーとする
- 主キーのカラムは `NULL` を許さず（`NULL in primary key column: {column}`）、値はテーブル内で一意とする（`duplicate primary key: {value}`）
- 主キーのないテーブルは、これまでどおりインデックスを持たない

### カタログの拡張

ADR-0005 のカタログレコードの末尾に次を追加する。

| サイズ | 内容 |
| --- | --- |
| 2 | 主キーのカラム番号（`u16`、0 始まり。主キーがなければ `0xFFFF`） |
| 4 | インデックスのルートページの Page ID（`u32`、主キーがなければ `0`） |

- ヘッダページのフォーマットバージョンを **`3`** に上げる。バージョン 3 以外のファイルは開かない（ADR-0005 と同じく、移行は行わない）

### ページ種別

ADR-0004 のページ種別の値を次のように使う。

| 値 | ページ |
| --- | --- |
| 1 | レコードページ |
| 2 | B+Tree ノード |

- Record Storage の追加・走査は、B+Tree ノードを読み飛ばす。Record ID が B+Tree ノードを指す場合は「レコードが存在しない」とする

### B+Tree ノードの形式

ノードヘッダ（16 バイト、リトルエンディアン）:

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 1 | ページ種別（`2`） |
| 1 | 1 | ノード種別（`1` = 葉、`2` = 内部） |
| 2 | 2 | キー数 `key_count`（`u16`） |
| 4 | 2 | 所有者のテーブル ID（`u16`） |
| 6 | 2 | 予約（ゼロ） |
| 8 | 4 | 葉: 次の葉の Page ID（なければ `0`）／内部: 最左の子の Page ID |
| 12 | 4 | 予約（ゼロ） |

葉のエントリ（16 バイト、オフセット 16 から並べる）:

| サイズ | 内容 |
| --- | --- |
| 8 | キー（`i64`） |
| 4 | 行の Page ID（`u32`） |
| 2 | 行の Slot ID（`u16`） |
| 2 | 予約（ゼロ） |

内部ノードのエントリ（12 バイト、オフセット 16 から並べる）:

| サイズ | 内容 |
| --- | --- |
| 8 | 区切りキー（`i64`） |
| 4 | 子の Page ID（`u32`） |

- エントリはキーの昇順に並べ、キーは符号付き整数として比較する
- 葉の最大キー数は `(4096 - 16) / 16 = 255`、内部ノードの最大キー数は `(4096 - 16) / 12 = 340` とする
- 内部ノードでは、最左の子は最初の区切りキーより小さいキーを、`i` 番目のエントリの子は `i` 番目の区切りキー以上で次の区切りキーより小さいキーを持つ

### 操作

検索:

- ルートから区切りキーに従って葉まで降り、葉の中を二分探索する

挿入:

- 葉がいっぱいなら、半分（小さい側が `⌈n/2⌉` 個）ずつ 2 つの葉に分割し、右側の最小キーを区切りキーとして親に挿入する。内部ノードの分割では、中央のキーを親へ上げる
- **ルートの Page ID は変えない**。ルートを分割するときは、新しいページを 2 つ確保して内容を移し、ルートを 2 つの子を持つ内部ノードとして書き直す。これによりカタログのルート Page ID を更新しなくてよい

削除:

- 葉からエントリを取り除くだけとし、ノードの併合・再分配は行わない。空になった葉もそのまま残す

### インデックスの保守

Table Operations（ADR-0006）の各操作で、主キーのあるテーブルのインデックスを更新する。

- テーブル作成時に、空の葉をルートとして確保する
- INSERT: 行を追加した後、キーと Record ID を挿入する
- DELETE: 行を削除した後、キーを取り除く
- UPDATE: 行の Record ID が変わった（ADR-0006 の移動）か、主キーの値が変わった場合に、古いキーを取り除いて新しいキーと Record ID を挿入する

一意性の検査は書き込みの前に行う（ADR-0008 の「すべて検査してから書き込む」規則に従う）。

- INSERT: 追加するすべての行について、既存のキーとも、同じ文の他の行とも重複しないことを確かめる
- UPDATE: 更新後のテーブル全体でキーが重複しないことを確かめる（対象外の行のキーと、対象行の新しいキーを合わせて検査する）。書き込みでは、対象行の古いキーをすべて取り除いてから新しいキーを挿入するため、`SET id = id + 1` のように一時的に重なる更新も成功する

### インデックスを使う条件

SELECT・UPDATE・DELETE の WHERE が次の形の条件を `AND` の項として含む場合、テーブル全走査の代わりにインデックスで行を 1 件引く。

```text
pk = 定数式   または   定数式 = pk
```

- 定数式とは、カラム参照を含まない式とする。その値が整数の場合だけインデックスを使い、それ以外（`NULL`、文字列など）の場合は全走査に戻す（エラーや結果を全走査と同じにするため）
- インデックスで引いた行にも WHERE 全体を評価する
- どの実行方法でも結果は同じになることをテストで確かめる。より一般的な実行計画の選択はステップ14（Query Planner）で扱う

### 観測

- 全走査をしていないことを確かめられるよう、Page Manager に読み込んだページ数の累計を数える仕組みを設け、`Database` から参照できるようにする

## Rationale

- 主キーを `INTEGER` 1 カラムに限ることで、キーを固定長にでき、ノードの形式と分割が単純になる
- ルートの Page ID を固定することで、分割のたびにカタログを書き換える必要がなくなる（SQLite と同じ方式）
- 削除時に併合を行わないことで、実装量を大きく減らせる。学習の主題である検索・挿入・分割は保たれる
- ページ種別で B+Tree ノードを区別するため、ADR-0004 の Record Storage と同じファイルに同居できる

## Consequences

### Positive

- 主キーによる検索がページ数に比例せず、木の高さ分のページ読み込みで済む
- 主キーの一意性と NOT NULL が保証される

### Negative

- 削除を繰り返すと、空の葉や疎なノードが残り、木が必要以上に大きくなる
- Record Storage の全走査は、B+Tree ノードも含めて全ページを読む
- フォーマットバージョンを上げるため、これまでのファイルは開けない
- 行の挿入とインデックスの挿入は別々に書き込まれるため、その間でクラッシュするとインデックスと行が食い違う（ステップ12で扱う）

## Non-goals

- 複合主キー、`TEXT` の主キー、二次インデックス、`CREATE INDEX`
- 範囲検索でのインデックス利用（ステップ14で扱う）
- ノードの併合・再分配
