# ADR-012: トランザクションの境界とロールバックの方式を定める

## Status

Accepted

## Context

ADR-0002 の実装順序では、Buffer Pool の次に Transaction を実装する。単一のトランザクションから始め、`BEGIN` と `COMMIT` でトランザクションの境界を導入する。この段階では高度な並行実行は扱わない。

ADR-0011 では、永続化の単位を SQL の 1 文とし、文がエラーで終わってもそれまでの変更を書き出していた。また ADR-0008 では、I/O エラーなどで文が途中まで適用されうることを Negative としていた。本 ADR では、トランザクションの構文と意味、ロールバックの方式、バッファプールとの関係を定める。

## Decision

### 構文

```text
statement := ... | BEGIN (TRANSACTION)? | COMMIT | ROLLBACK
```

- キーワードに `BEGIN`、`COMMIT`、`ROLLBACK`、`TRANSACTION` を追加する
- 結果の表示は `BEGIN`、`COMMIT`、`ROLLBACK` とする

### 意味

- `Database` は、明示的なトランザクションの中にあるかどうかの状態を持つ。トランザクションは同時に 1 つだけとする
- `BEGIN` は明示的なトランザクションを始める。すでに中にある場合はエラー（`transaction already in progress`）とする
- `COMMIT` はトランザクションの変更を永続化して終える。`ROLLBACK` は変更をすべて取り消して終える。トランザクションの外で実行した場合はエラー（`no transaction in progress`）とする
- トランザクションの外の文は、その文だけのトランザクション（自動コミット）として実行する
- `CREATE TABLE` もトランザクションの一部であり、ロールバックで取り消される

### 文の原子性

- **文がエラーで終わった場合、その文の変更をすべて取り消す**
- 明示的なトランザクションの中で文がエラーになっても、トランザクションは続く。取り消されるのはその文の変更だけで、それより前の文の変更は残る（SQLite と同じ）
- これにより ADR-0008 の「すべて検査してから書き込む」規則は、書き込み中のエラー（I/O エラー、ページに入らない行など）に対しても原子性を持つようになる

### ロールバックの方式（no-steal）

トランザクションの変更はバッファプールの dirty なページにだけ存在し、コミットするまでディスクに書かない。

- **dirty なページは eviction の対象にしない**。追い出せるのは dirty でないページだけとする
- 追い出せるページがない場合は、フレーム数の上限を一時的に超えてフレームを追加する。コミット・ロールバックの後、上限を超えた分は dirty でないページから追い出して元に戻す
- コミット: ADR-0011 の flush を行う
- トランザクションのロールバック: dirty なページをすべて捨て、バッファプールのページ数をディスク上のページ数に戻す（確保したページも捨てる）
- 文のロールバック: 文の開始時に **セーブポイント** を設ける。セーブポイントの後でページを最初に書き換えるときに、書き換える前の内容（とその時点で dirty だったか）を記録する。文がエラーになったら、記録した内容をフレームに戻し、セーブポイントの後に確保したページを捨てる
- ロールバックの後は、メモリ上のカタログ（テーブルのスキーマ）をページから読み直す

### 終了時

- 明示的なトランザクションの途中で DB を閉じた場合（プロセスの終了を含む）、変更はディスクに書かれていないので、ロールバックしたのと同じになる
- REPL は、入力の終わりでトランザクションが残っていれば `warning: transaction rolled back` を標準エラーに表示する
- REPL のプロンプトは、トランザクションの中では `sqltoy*> ` とする

### 公開インターフェース

- `Database` に、トランザクションを始める・コミットする・ロールバックする操作と、トランザクションの中かどうかを返す操作を追加する
- 行操作の API（ADR-0006）とテーブル作成は、それぞれを 1 つの文として扱う

## Rationale

- no-steal にすれば、コミット前の変更はディスクに存在しないので、ロールバックはメモリ上の dirty なページを捨てるだけで済む。取り消しのためのログ（undo log）が不要になる
- 文のロールバックを書き換え前のページの記録で行うことで、テーブル操作・B+Tree・カタログのどの変更も、層ごとの取り消し処理なしに一様に戻せる
- トランザクションの中のエラーでトランザクション全体を失敗させない方式は、REPL で試すときに扱いやすい

## Consequences

### Positive

- `BEGIN` から `COMMIT` までの変更をまとめて永続化し、`ROLLBACK` で取り消せる
- 文が途中まで適用されることがなくなる（クラッシュを除く）

### Negative

- トランザクションで変更したページはすべてメモリに載る必要がある。大きなトランザクションではバッファプールが上限を超えて大きくなる
- コミットの flush が複数のページを書く途中でクラッシュすると、変更の一部だけがディスクに残る（ステップ12で扱う）
- 同時に複数のトランザクションを扱えない（ステップ13で扱う）
- 複数のプロセスが同じファイルを同時に開くことは防いでいない

## Non-goals

- SAVEPOINT 構文、入れ子のトランザクション
- 並行実行、ロック
- プロセス間の排他
